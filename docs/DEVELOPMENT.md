# Разработка, запуск и выпуск tile-rs

## Запуск после изменения кода

Откройте PowerShell в папке проекта. Для сборки из исходников нужны Windows 10/11 x64, Rust
stable и Visual Studio Build Tools с компонентом **Desktop development with C++**.

```powershell
. .\scripts\vcenv.ps1      # подключить окружение MSVC для текущего PowerShell
cargo run                 # debug-сборка, приложение работает через трей
cargo run --release       # оптимизированный запуск
cargo run -- --version    # показать версию
cargo run -- list         # показать найденные окна и причины пропуска
cargo run -- tile         # разложить окна один раз и завершить работу
```

Первый обычный запуск открывает лаунчер настроек и оставляет tile-rs в системном трее. Выходите
через меню значка в трее → **Quit tile-rs**. Не запускайте его параллельно с другим оконным
менеджером. Лог находится в `%LOCALAPPDATA%\tile-rs\tile-rs.log`, конфиг — в
`%APPDATA%\tile-rs\config.toml`.

## Структура папки проекта

- `src/` — Rust: управление окнами, рабочие столы, системный трей и анимации.
- `ui/` — исходник интерфейса Slint; встраивается при сборке, отдельно устанавливать его не нужно.
- `assets/` — значок приложения; `installer/` — исходник установщика Inno Setup.
- `scripts/` — проверки, упаковка, подпись и сборка установщика.
- `docs/` — настройка, разработка, ограничения анимаций и выпуск версий.
- `.github/workflows/` — CI и публикация релиза; `.cargo/` — параметры статической сборки.
- `target/` — локальные сборки и кэш Cargo; `release/` — ZIP и SHA-256; `dist/` — установщик.
  Эти три папки не входят в Git. Для запуска оптимизированной версии используйте
  `target\release\tile-rs.exe`, а для распространения — файлы из GitHub Releases.

Личные настройки помощников и черновики планов исключены из Git. Настройки пользователя и
логи программы хранятся в AppData, отдельно от исходников и релизных файлов.

## Структура исходного кода

```text
src/
  main.rs                    точка входа
  app/                       состояние и координация менеджера окон
    mod.rs                   State, общие типы и доступ к подсистемам
    startup.rs               запуск, цикл сообщений, завершение
    cli.rs                   команды терминала
    events.rs                WinEvent, отложенные события, очистка данных окна
    event_queue.rs           очередь с объединением событий движения
    placement.rs             размещение окон, рамки, пакетные операции
    tiling.rs                пересчёт раскладки, вместимость, изменение размеров
    animation.rs             анимации, таймеры, ограничения размеров клиента
    workspaces.rs            рабочие столы, фокус, восстановление окон
    monitors.rs              сохранение назначений при изменении мониторов
    interaction.rs           перетаскивание разделителей и индикатор столов
    actions.rs               регистрация горячих клавиш и выполнение команд
    border.rs                рамка фокуса
    report.rs                диагностический отчёт
    tests.rs                 регрессионные тесты координации
    window_lifecycle_tests.rs тесты жизненного цикла окон
  layout/                    геометрия раскладок, разделители, очередь resize
  platform/                  окна и мониторы Windows, автозапуск, уведомления,
                             восстановление припаркованных окон, обновления
  ui/                        лаунчер Slint, его модель, трей, нативные оверлеи
  config/                    настройки, миграция, имена команд и разбор клавиш
  diagnostics/               логирование и профилирование
```

`app` хранит состояние в потоке цикла сообщений; дочерние модули работают с ним через
родительский модуль. При выделении файлов сохранены границы транзакций вокруг Windows API:
вложенные события откладываются до освобождения заимствования `State`. Единая очистка данных
окна остаётся в `app/events.rs` (`drop_window_data`). Имена действий и разбор клавиш находятся
в `config`, чтобы интерфейс мог использовать их без обращения к состоянию менеджера.

## Проверка изменений

Перед отправкой изменений запускайте полный локальный набор проверок:

```powershell
./scripts/check.ps1
```

Он проверяет форматирование, Clippy без предупреждений, все тесты и release-сборку. Отдельные
команды:

```powershell
cargo fmt --all -- --check
cargo clippy --all-targets -- -D warnings
cargo test --all-targets
cargo build --release
```

После автоматических проверок вручную проверьте tray, лаунчер, сохранение/перезагрузку настроек,
горячие клавиши, переключение рабочих столов, изменение размера окон, полноэкранные приложения и
автозапуск. Для правок многомониторной логики дополнительно проверяйте независимое переключение
столов на каждом мониторе, перенос окна между мониторами, отключение/подключение экрана и разные
DPI. Первую установку проверяйте под отдельной учётной записью Windows или в Windows Sandbox,
чтобы не трогать личный конфиг.

## Локальный portable-пакет

```powershell
./scripts/package.ps1
```

Скрипт собирает release, кладёт в `release/` архив
`tile-rs-v<VERSION>-windows-x64.zip` и файл `.sha256`. В архив входят `tile-rs.exe`, оба README,
лицензия, changelog и папка `docs/` со справочником конфигурации, описанием анимаций и инструкциями.
Скрипт заменяет staging-папку и архив только
текущей версии, не удаляя другие файлы из `release/`.

## Установка для пользователей

Для обычных пользователей рекомендуемый файл — `tile-rs-<VERSION>-setup.exe`, который собирает
GitHub Actions. Мастер копирует приложение, предлагает ярлык и автозапуск и может запустить его
после установки. Портативная альтернатива — ZIP: распаковать и запустить `tile-rs.exe`.

Пользователю не нужны Rust, Visual Studio или отдельный установщик библиотек: приложение не
использует внешние runtime-пакеты, а release-сборка статически включает MSVC C runtime. Системные
Windows API уже есть в Windows 10/11. Rust и C++ Build Tools нужны только тем, кто собирает проект
из исходников. Настройки и логи находятся вне папки программы и переживают обновление/удаление.

## Публикация GitHub Release

Релизный workflow запускается только тегом `v<VERSION>` на опубликованном коммите `main`. Он
проверяет тег, запускает форматирование/Clippy/тесты и release-сборку, затем публикует ровно эти
файлы:

- `tile-rs-v<VERSION>-windows-x64.zip` и его SHA-256;
- `tile-rs-<VERSION>-setup.exe`.

Версия берётся из `Cargo.toml`. Изменения сначала вливаются в `main` через pull request; затем
создаётся и отправляется тег. Подробнее: [процесс выпуска](RELEASING.md).
