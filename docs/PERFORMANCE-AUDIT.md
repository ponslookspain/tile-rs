# Аудит производительности — 19 октября 2026

Изменения находятся в `codex/performance-foundation`, поверх выпущенной версии 0.5.0.
Опубликованные файлы 0.5.0 эти изменения не содержат. Новых Rust-зависимостей нет.

## Что исправлено

| Участок | Изменение и ожидаемый эффект |
|---|---|
| События окон | Повторные координаты объединяются внутри сегмента между событиями жизненного цикла. Replay обрабатывает не более 64 событий за проход и проверяет бюджет 4 мс между обработчиками. Это не ограничивает длительность одного вызова Windows. |
| Планирование | Основной цикл также уступает управление после 64 сообщений/4 мс. Таймер кадров не принимается за сигнал при отсутствии waitable handle. |
| Перестроение | Невидимый CREATE и HIDE/DESTROY неизвестного окна не вызывают лишнее сканирование. Debounce перестаёт переносить срок после 120 мс потока событий; WM_TIMER по-прежнему зависит от очереди Windows. |
| Упрямые приложения | Не более трёх корректирующих перемещений для неизменной цели; ручной resize, Retile, переключение рабочего стола и reload сбрасывают историю. Смена цели начинает новый бюджет. |
| Частота | `animation_fps_limit = 60` по умолчанию, диапазон 15–240. Частота дисплея кешируется до изменения рабочей области. Это таймерное планирование, без гарантии vsync. |
| Живой resize | Снимки и их GPU-ресурсы удалены. На окно хранится одна неотправленная цель; новые движения её заменяют. Если предыдущий размер ещё не наблюдается, следующая отправка откладывается до 90 мс. Быстрые соседи продолжают обновляться независимо. |
| Отрисовка | Приложения сами перестраивают содержимое. Переиспользуются окна разделителей; захваченный разделитель следует за зазором, остальные скрыты до отпускания. |
| Память служебных данных | Удаляются устаревшие ключи движений при непрерывной очереди; профилирование хранит последние 4096 образцов на метрику. |
| Сеть | Проверка обновлений в отдельном потоке, одна незавершённая проверка на процесс. Проверяются HTTP-статус, ошибки чтения, размер ответа и версии. |
| Настройки | Запись полного временного файла, flush, затем замена. Ошибка записи/замены сохраняет прежний config. Миграция сначала сохраняет резервную копию. |
| Разработка | Диагностика и очередь вынесены из main; CI и релиз используют общий ключ кеша зависимостей. Сборка установщика переиспользует уже собранный exe. |

## Что ещё требует работы

1. **Приоритет высокий: зависшие приложения.** Размещения используют `SWP_ASYNCWINDOWPOS`,
   фактическая геометрия проверяется отдельно. Троттлинг ограничивает частоту новых отправок,
   но не отменяет уже принятые Windows запросы и не ускоряет чужую компоновку/отрисовку.
2. **Приоритет высокий: измерения на оборудовании.** Нужны реальные p95/p99 времени кадра,
   CPU/GPU и private bytes на слабом компьютере, при 30 и 60 FPS живого resize. Ускорение в
   процентах пока не измерено; тесты с собственными Win32-окнами не заменяют эти измерения.
3. **Приоритет средний: идентичность процессов.** Существующие кеши имени и elevation
   ограничены размером, но ключуются PID. Следует учитывать время создания процесса или
   удерживать проверяемый handle, чтобы исключить устаревшее значение после повторного PID.
4. **Несколько дисплеев — сделано, нужна проверка на железе.** Частота обновления читается для
   каждого монитора. Таймер кадров идёт в темпе самого быстрого монитора, на котором сейчас
   есть анимация (а не самого быстрого вообще), а окна на более медленном мониторе пропускают
   лишние тики (`frame_due`). Привязка к vsync сохранена, только когда анимируется самый
   быстрый монитор: компоновщик отдаёт одни часы обновления. Финальный кадр не пропускается.
   Остаётся замерить смешанную конфигурацию, например 60 + 144 Гц.
5. **Приоритет средний: границы состояния.** Данные окна частично собраны в `TrackedWindow`
   (identity, pending_monitor, float_reason). Остальные карты по `hwnd` намеренно оставлены
   отдельными: очистка централизована в `drop_window_data` и закрыта двумя тестами, один из
   которых проверяет по исходнику, что каждая новая коллекция `State` с ключом окна там
   обработана. Дальнейший перенос даёт мало и затрагивает ~300 мест в хрупком коде.

## Настройка для слабого компьютера

В верхней части конфигурации: `animation_fps_limit = 30`, `focus_follows_mouse = false`.
Снимков больше нет. Понижение лимита кадров уменьшает число реальных resize чужих приложений.
`animations = false` отключает анимации перестановки, но сохраняет живое перетаскивание тайлов.
Сначала завершить прежний экземпляр через трей, затем запустить `target\release\tile-rs.exe`.

## Проверка

Автоматические проверки: форматирование, Clippy с запретом предупреждений, unit/Win32-тесты,
release-сборка. Проверены бурсты 200 000 движений, барьеры CREATE/DESTROY, ограничение памяти
ключей, разворот resize, бюджет повторов, объединение целей и независимый троттлинг окон,
возврат реальной геометрии при отмене и ошибка замены заблокированного файла.
Тесты не доказывают отсутствие визуальных рывков в браузере или зависания чужого UI-потока.

Ручной прогон: браузер + Explorer + редактор; быстрые reversals при resize, удержание горячих
клавиш, создание/закрытие/сворачивание соседей, Escape, смена рабочих столов и монитора,
отключение монитора, разные DPI, затем повтор при 30 и 60 FPS.
Для сравнения включить `TILE_RS_PROFILE=1`: лог содержит длительности layout/batch, placement,
интервалы кадров и счётчики очереди. Сравнивать одинаковые сценарии, отдельно холодный старт.

Настройки общего кеша — в [официальном rust-cache](https://github.com/Swatinem/rust-cache).
